# 怎么验证「别人装上去 = 我这台的效果」

一共四层，从弱到强。前两层任何人 5 分钟能跑完，后两层是真正的效果等价证明。

## 0. 先说结论：什么算「同一个效果」

`dsh-purge` 的效果 = **宿主被改写成什么样**，与下面这些无关：

| 会影响结果的东西 | 会不会影响 |
| --- | --- |
| 宿主 dsh 版本（`0.2.1-rc.2` vs 其它） | **会**，锚点/文件内容不同，必须同版本 |
| 插件源码（本仓库的 `lib/`） | **会**，这就是被验证的对象 |
| 用户自己的 `$DSH_HOME/prompt-inject.md` | **会**，这是注入正文，天然人人不同 |
| 模型、账号、网络 | **会**，回答风格不同；不影响宿主改写结果 |
| 操作系统 / 用户名 / 安装路径 | 不会（哈希里不含路径） |

所以可对齐的硬指标是四个：**插件版本 + 宿主版本 + 破甲内核哈希 + 每个被改写文件的 sha256**，外加**每条补丁的状态**（该落刀的必须 `applied`，不能是 `pending` / `skipped`）。

## 1. 仓库内容：上传的 == 本地的

```bash
node scripts/verify-pro.mjs --repo            # 默认对比 master
node scripts/verify-pro.mjs --repo --ref v1.1.72-dsh021
```

做法：从 `codeload.github.com` 拉该 ref 的 tarball，gunzip + 手写 tar 解析，逐个文件算 sha256 和本地目录比。

期望输出：

```
ref=master 远端=113 本地=113
结论: PASS — 远端 master 与本地源码逐文件一致（113 个文件）。
```

出现 `✗ 内容不同` / `✗ 远端有本地无` 就是没推干净（换行符、漏 add、GitHub 上被手改）。

> 比较时对文本文件做换行符归一化（CRLF → LF）：`core.autocrlf=true` 的 Windows 工作区是 CRLF，仓库里存的是 LF；二进制文件（含 NUL 字节）按原始字节比。

## 2. Release 资产：zip == 这个 tag 的源码

```bash
curl -LO https://github.com/feeling6667/dsh-purge-pro/releases/download/v1.1.72-dsh021/dsh-purge-1.1.72-dsh021.zip
sha256sum dsh-purge-1.1.72-dsh021.zip     # 和本地 `git archive` 出来的比
```

## 3. 效果基线：`verification/baseline-dsh0.2.1-rc.2.json`

基线里存的是：

```jsonc
{
  "plugin": { "version": "1.1.72-dsh021", "commit": "…" },
  "host":   { "versions": { "dsh": "0.2.1-rc.2" } },
  "kernel_sha256": "111bcf3a…",          // 内置破甲提示词的哈希（defaultOverrideHash）
  "dryRun": { "patches": 82, "patchesChanged": 60, "files": 53 },
  "patches": [ { "id": 1, "changed": 1, "status_after": "applied", "files": ["…"] }, … ],
  "files":   { "dsh-agent-instructions/lib/index.js": "3ac195f5…", … }   // 53 个目标文件的最终 sha256
}
```

生成方式（基准机上）：

```bash
node scripts/verify-pro.mjs --baseline <未清洗的@deepseek-ai> <已清洗的@deepseek-ai> --surface desktop
```

它做两件事：对**未清洗**宿主树跑纯内存 dry-apply，得到每个文件的最终哈希；再拿这份结果和**已清洗**树逐文件比。本仓库这份基线生成时 `与已清洗树逐文件对照: 0 处不同`。

## 4. 在别人机器上自证：`--check`

```bash
git clone https://github.com/feeling6667/dsh-purge-pro
cd dsh-purge-pro
node scripts/verify-pro.mjs --check
```

它读当前宿主的 `@deepseek-ai`（`core.findAiBase()`，也可 `--ai-base` 指定），做四件事：

1. 宿主 `dsh` 版本 == 基线版本；
2. `defaultOverrideHash()` == 基线内核哈希（证明装的是同一份破甲提示词）；
3. 82 条补丁状态：基线里 `changed > 0` 的必须 `applied` / `already`，其余不许 `pending`；
4. 53 个目标文件 sha256 逐个比。

期望输出：

```
  ✓ 宿主版本 dsh               本机 0.2.1-rc.2 / 基线 0.2.1-rc.2
  ✓ 破甲内核哈希                 本机 111bcf3a26ec7e30… / 基线 111bcf3a26ec7e30…
  ✓ 补丁状态 82 条              全部与基线一致
  ✓ 目标文件 53 个              sha256 全部一致

结论: PASS — 效果与基线一致。
```

退出码 `0` = 一致，`1` = 有差异（CI 里可以直接当闸门）。

### 这一层真的有效吗

本仓库发布前做过一次端到端对照：把未清洗宿主的 53 个目标文件复制到独立目录，用 `DSH_BASE` / `DSH_HOME` 指过去，走**插件真实写入路径** `applyPatchesAllHosts()`（不是 dry-run），再和基线比：

```
apply 状态分布: { applied: 60, already: 6, missing_file: 15, skipped: 1 }
真实 apply 结果 vs dry-apply 基线：0 / 53 个文件不同
```

> `missing_file: 15` 是因为这次只镜像了目标文件、没有桌面壳和 asar，不是真实机器的分布；真实安装上这些会是 `applied` / `already`。

反向也测过：在任意一个目标文件末尾加一行 `// tampered`，`--check` 立刻报

```
  ✗ 目标文件 53 个              1 个不一致
    ✗ dsh-agent-instructions/lib/index.js 本机=f3afa1c0d5d2 基线=3ac195f57618
结论: FAIL — 1 项不一致。
```

注意这一条：补丁状态仍是 `applied`（标记还在），**只有哈希能抓出来**。所以别只信面板上的对勾。

## 5. 已知边界

- **宿主版本不同，哈希必然不同**，这不是失败。要在别的 dsh 版本上验证，得在该版本上重新 `--baseline`。
- `$DSH_HOME/prompt-inject.md` 是用户自己的正文，不进基线；它变了，回答风格会变，但宿主改写结果不变。
- 补丁会在宿主文件旁边留 `.dshpurge.bak`，基线不包含这些备份文件。
- 桌面端还有 asar 重打包、shim 注入（`dsh.cmd` / `dsh.ps1`）这些**不在 53 个文件里**的副作用；`--check` 覆盖的是「宿主 JS 代码被改成什么」，shim 层看 `dsh-purge --status` 的 `shim:` 行。
- 真正的「回答效果」还受模型影响：同一份宿主 + 不同模型，破甲表现不同。这部分没有机器可验的等价物，只能人工对比。
